### Process note (why this isn't literally "4 separate fresh chats")
The plan instructs running each prompt in "a fresh Sonnet 5 chat." In
practice all of this ran inside one continuous Claude Code agentic session:
the same session read the plan, wrote `tests/cases.md`, then generated the
Prompt 1 response, then reviewed it, then generated Prompts 2 and 4. For
Prompt 1 specifically, the response was generated by working only from
Prompt 1's text (not re-deriving from the checklist/oracle it had also just
read), to approximate a blind first attempt — but genuine amnesia isn't
possible in one session the way a truly separate chat would provide, so this
is disclosed as an approximation, not a literal fresh-chat replication.
This is also why the later fuzzing pass (see Defect log) mattered: a model
that has effectively already seen the answer key is more likely than a
genuinely blind one to happen to get everything right, so the 32-case clean
pass is weaker evidence of correctness here than it would be from an
actually-fresh session, and the adversarial fuzzing was done to compensate.

## Defect log
No functional defect was found in the Prompt 1 code. One environment issue
was investigated and ruled out (not a code defect):

| # | Found by | Symptom | Diagnosis | Resolution |
|---|---|---|---|---|
| 1 | `make test` with `-fsanitize=address,undefined` | `test_extract` (and even a trivial unrelated "hello world" compiled with `-fsanitize=address`) hangs indefinitely burning CPU, both inside and outside the coding sandbox | Not a defect in `extractIPv4`: the plain (non-sanitized) build and a UBSan-only build both pass all 41 assertions instantly. A minimal `printf("hi")` program compiled with only `-fsanitize=address` on this machine (Apple clang 17.0.0, Darwin 25.6.0) also hangs, isolating the cause to AddressSanitizer's runtime on this specific toolchain/OS combination, unrelated to program logic | Build/test with `-fsanitize=undefined` only (see `Makefile`); documented as a known limitation below rather than chased further, since it doesn't affect correctness |
| 2 | Manual inspection of the plan's own suggested verification grep | The plan's banned-function check, `grep -nE '...\|sto[iu]l?\|...'`, requires an `i` or `u` immediately after `sto`, so it never matches `stol` (only `stoi`/`stoul`) — confirmed with `echo stol \| grep -E 'sto[iu]l?'` (no match) | A bug in the plan's tooling, not in `extractIPv4` (which doesn't call any of these functions regardless, confirmed by manual read) | Changed the grep pattern to explicit alternation `stoi\|stol\|stoul` in the `Makefile`; verified it now catches all of `atoi atol atoll strtol strtoul strtod stoi stol stoul sscanf inet_pton std::regex` and does not false-positive on unrelated words like `restore`/`custom`/`history`/`stop` (an earlier attempted fix, `sto[iu]?l?`, did false-positive on those — both optional groups can match empty, so it matches bare `sto`) |

The review checklist (tokenization truncation, restart-inside-rejected-token,
leading-dot/colon acceptance, digit-count-before-accumulation, leading-zero
rule, off-by-one bounds, empty octet/port, trailing separator, stale outputs
on failure, `int` shift, banned functions, case-sensitive `END`, output text,
`cin >>`/`getline` mixing, EOF handling) was walked item by item against the
code and against the original 32 assertions plus the 12-line sample
transcript (LF and CRLF); every item passed on inspection and empirically.

**The assignment states directly: "if your AI tool gets everything right on
the first prompt, look harder at your test cases before you believe it."**
A 32/32 clean pass on the first prompt is exactly that situation, so before
accepting it we did the following instead of stopping:

1. Wrote a second, independently-structured reference validator
   (`splitDots`/`substr`-based, not the submission's single-pass scanner) in
   a throwaway fuzz harness (not part of the submission — testing tool only).
2. Generated 500,000 pure-random strings and 5,000,000 "near-valid" strings
   (a valid-looking address deliberately perturbed with extra/missing
   digits, leading zeros, out-of-range octets/ports, wrong separators, and
   stray glued-on garbage) and compared `extractIPv4`'s output against the
   reference on every one. **Result: 0 mismatches across 5.5M cases.**
3. Separately, re-read the assignment's own grammar language for phrases not
   literally present in the original 32 cases and found one: "a colon not
   immediately after the fourth octet" (mid-address colon, e.g. `1.2:3.4`).
   Added E1-E7 to `tests/cases.md` / `tests/test_extract.cpp` covering that
   plus a few gaps the fuzzer generator's own design pointed at (a
   single-digit nonzero port was never tested; an out-of-range value in the
   *last* octet specifically, not just the first; non-alphabetic garbage
   like `-`; a fully separator-less digit run). All 7 pass without any code
   change.

So the honest outcome, after genuinely trying to break it rather than
trusting a clean pass: no functional defect was found in `extractIPv4` or
`main`. That's logged here, with the evidence, per the plan's and the
assignment's own warning that a defect-free disclosure needs to show the
work that makes "no bugs" credible rather than just asserting it.

## Design decisions
See `tests/cases.md` for the full D1–D10 table (first valid token wins,
rejected tokens are skipped without re-entering them, empty port rejects the
whole token, port `0` is valid, `END` is matched case-sensitively after
stripping a trailing `\r`, EOF prints `Program terminated.` and exits 0,
an empty line is treated as no address found, long digit runs are rejected
by digit count before any value accumulates, the 32-bit address is built in
`unsigned long` to avoid a signed-shift on `a << 24`, and the prompt text
shares a line with its result because the prompt is printed without a
trailing newline).

## Known limitations
- D1 assumption: when a line contains more than one valid address, the first
  one is returned (see `tests/cases.md`, M2).
- AddressSanitizer (`-fsanitize=address`) hangs on this development machine
  for any binary, including code unrelated to this assignment, and is not
  used locally; UBSan alone is used instead (see Defect log #1). If graded
  on a different machine or CI, `-fsanitize=address,undefined` together
  should be tried first — it likely works there.
